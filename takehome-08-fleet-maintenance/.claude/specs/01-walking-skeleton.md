# Spec 01 - Walking Skeleton

## Overview

Stand up the repository, the monorepo structure and a deployment pipeline that is
proven end to end before any business logic exists. A hello-world request travels
Vercel to Render to Supabase and back: the browser renders one row that was read
from Postgres through SQLAlchemy, behind a migration applied by Alembic. This is
Phase 1 and Phase 2 of the CLAUDE.md Development Order. It satisfies no assignment
goal on its own; it is the precondition for all ten, because it converts
deployment from an hour-11 risk into a solved problem every later phase inherits.

None. This is the first feature. Everything else depends on it.

## Data model

One table, created by the first Alembic migration. It exists to prove the
migration chain and the read path, and it is the only schema this feature adds.
The real schema is Phase 3.

`deployment_check`

| column     | type        | constraints                        |
|------------|-------------|------------------------------------|
| id         | integer     | primary key, generated by identity |
| label      | text        | not null                           |
| checked_at | timestamptz | not null, default `now()`          |

Migration `0001_deployment_check`:

* creates the table
* inserts exactly one row with label `fleet-maintenance walking skeleton`
* has a working `downgrade()` that drops the table

Alembic is configured here - `alembic.ini`, `migrations/env.py` reading
`DATABASE_URL` from the environment, never a hard-coded URL. The migration must
run against Supabase, not only against a local Postgres. A migration that has
only ever run locally has not proven anything this phase exists to prove.

## Business rules

1. `GET /health` returns 200 with `{"status": "ok", "database": "ok"}` only when a
   `SELECT 1` against the configured database succeeds. If the query raises, it
   returns 503 with `{"status": "degraded", "database": "unreachable"}`. It must
   never report healthy without touching the database - a health check that only
   proves the process is running is what lets a broken `DATABASE_URL` reach
   production unnoticed.
2. `GET /api/deployment-check` returns the single `deployment_check` row. If the
   table is empty it returns 404 naming the missing migration seed, rather than
   200 with a null body.
3. The API starts only with `DATABASE_URL` set. A missing or unparseable value
   fails at startup with a clear message. It must not fail lazily on the first
   request.
4. `CORS_ORIGINS` is read from the environment as a comma-separated list and is
   the only allowed set of origins. `*` is not permitted in the deployed
   configuration, and credentialed CORS with `*` must not be configured at all.
5. No secret is committed. `.env` is gitignored; `.env.example` is committed and
   lists `DATABASE_URL`, `JWT_SECRET`, `CORS_ORIGINS` and
   `OVERDUE_GRACE_PERIOD_DAYS` with placeholder values only.

## API

| method | route                   | auth | authorization | request | response            | errors |
|--------|-------------------------|------|---------------|---------|---------------------|--------|
| GET    | `/health`               | none | none          | none    | `{status, database}` | 503 database unreachable |
| GET    | `/api/deployment-check` | none | none          | none    | `{id, label, checked_at}` | 404 no row, 503 database unreachable |

Routes live in `apps/api/app/api/`, thin, delegating the read to a repository call
in `apps/api/app/repositories/`. Even at this size the layering from the CLAUDE.md
API Architecture section is established, because the shape set here is the shape
every later phase copies.

## Frontend

`apps/web` - Next.js (App Router), TypeScript, Tailwind, TanStack Query configured
with a shared query client. shadcn/ui initialised so later phases add components
rather than bootstrapping.

One page, `/`, which fetches `/api/deployment-check` through a typed API client in
`apps/web/lib/` that reads the backend base URL from `NEXT_PUBLIC_API_BASE_URL`.
The base URL is never hard-coded in a component.

Required states on that page:

* loading - a skeleton or spinner while the query is in flight
* error - the failure surfaced as readable text including the status code, not a
  blank screen and not a silent console log
* empty - distinct from error; shown when the request succeeds but no row exists
* success - the row's `label` and `checked_at` rendered

Proving the error state renders correctly is part of this feature, not polish. It
is the state most likely to be hit first in production.

## Tests

Pytest, in `apps/api/tests/`, written in this phase.

1. `GET /health` returns 200 and `database: "ok"` against a live test database.
   (rule 1)
2. `GET /health` returns 503 and `database: "unreachable"` when the database
   session raises on connect. (rule 1)
3. `GET /api/deployment-check` returns 200 and the seeded label. (rule 2)
4. `GET /api/deployment-check` returns 404 when the table is empty. (rule 2)
5. Application startup raises with a clear message when `DATABASE_URL` is absent.
   (rule 3)
6. `alembic upgrade head` applies cleanly to an empty database and
   `alembic downgrade base` reverses it. (data model)

Test 6 matters more than its size suggests: it is the check that the migration
chain is reversible while there is still only one migration in it.

## Risks and open questions

1. **Repo root - needs a decision before Phase 1 completes.** CLAUDE.md states
   "The repository is not yet a git repository", but this project is nested inside
   an existing repo at `busy/` alongside unrelated files. Either the project
   directory becomes its own repository with its own public GitHub remote
   (matching CLAUDE.md, and what a reviewer expects to clone), or it stays nested
   and the submitted repo carries unrelated content. Recommend the former. Until
   it is settled, `git init` cannot be run correctly.
2. **Supabase pooling.** Supabase's pooled connection string (pgbouncer,
   transaction mode) does not support prepared statements the way the default
   SQLAlchemy driver setup expects. Expect to either use the direct connection
   string for Alembic and the pooled one for the app, or disable statement
   caching. This is the most likely cause of a migration that works locally and
   fails on Supabase.
3. **Render cold starts.** A free-tier backend sleeps. The first request after
   idle can take tens of seconds, which reads as a broken frontend during a demo.
   The loading and error states above are the mitigation; decide whether a
   keep-alive is worth it before the final walkthrough.
4. **Open question for the user:** the public GitHub repository name and owner,
   needed for `git remote add origin`.
